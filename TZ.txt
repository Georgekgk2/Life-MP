Нижче — готове **ТЗ і план передачі іншому агенту**. Його можна копіювати як стартовий документ у задачу; рекомендую вимагати від агента спочатку пройти фазу Discovery і затвердити рішення, а не починати реалізацію з припущень.

## 1. Мета продукту

Створити українську мультивендорну платформу **«ЛАЙФ»** у блакитно-білій стилістиці, яка об’єднує:

- продаж еко‑, натуральних і авторських товарів;
- профілі виробників, майстрів, експертів і практиків;
- послуги та практики, що потребують заявки або запису;
- тренінги, майстер‑класи та інші події;
- editorial‑контент: історії, відео, корисні матеріали;
- благодійні ініціативи та сторінки партнерів;
- affiliate / реферальну програму для контент‑партнерів.

Проєкт не повинен виглядати як «ще один інтернет‑магазин». Основна ідея — **живий простір людей, майстрів, товарів, знань і практик**, де товар є частиною історії людини або бренду.

***

## 2. Продуктові принципи

1. **Контент перед продажем.** Кожен виробник/майстер має профіль, історію, медіа та перелік пропозицій.
2. **Один каталог, різні типи пропозицій.** Товари, послуги, події та благодійність показуються в спільній навігації, але мають різну бізнес‑логіку.
3. **Мультивендорність.** Кожен виробник у майбутньому керує власним каталогом, замовленнями та профілем у межах своїх прав.
4. **Affiliate лише за підтверджені продажі.** Немає вступних внесків, «інвестицій», винагород за вербування або необмеженої багаторівневої структури.
5. **Публічні claim-и проходять модерацію.** Платформа не повинна автоматично публікувати медичні або лікувальні обіцянки.
6. **Mobile-first.** Основний трафік очікується з Instagram, TikTok, Telegram та посилань від блогерів.
7. **Швидкий перший реліз.** Спочатку концепт, каталог і продаж нехарчових/нескладних товарів; складні категорії підключаються поступово.

***

## 3. Межі MVP

### Входить у MVP

- Головна сторінка та каталог.
- Категорії, підкатегорії, бренди/майстри.
- Профілі виробників і практиків.
- Товари, варіанти, ціни, залишки, фото, характеристики.
- Контентні сторінки: історії, відео, добірки.
- Кошик і checkout для товарів.
- Базова інтеграція Нової пошти.
- Один український payment provider після його вибору замовником.
- Кабінет платформи.
- Vendor onboarding та обмежений кабінет виробника.
- Affiliate tracking: лінк → перехід → атрибуція → підтверджене замовлення → комісія.
- Заявки на послуги та події, без складного календаря бронювань.
- Cloudflare, CDN, object storage, backups, базовий моніторинг.
- Staging та production deployment.

### Не входить у MVP

- Мобільні застосунки iOS/Android.
- Складський облік, закупівлі та власний fulfillment.
- Відеохостинг і transcoding на власному сервері.
- Свіже м’ясо, готова їжа, холодовий ланцюг та доставка день-у-день.
- Повноцінний календар із бронюваннями, депозитами, переносами та no-show policy.
- Продаж квитків із автоматичними QR‑квитками.
- Автоматичні банківські виплати афіліатам.
- Self-hosted PostHog, ClickHouse, Kafka, Meilisearch.
- Розподілена мікросервісна архітектура.
- AI‑помічник, LLM‑пошук чи персональні рекомендації.
- Публічний «знак якості» без затверджених правил і процедури підтвердження.

## 4. Пропонований стек

| Шар | Рішення | Обґрунтування |
|---|---|---|
| Storefront | Next.js, TypeScript, App Router | SEO, SSR/ISR, висока швидкість на мобільному, зручна інтеграція з Medusa |
| Commerce | Medusa v2, TypeScript | Commerce API, carts, orders, payments, inventory, custom modules/workflows |
| Marketplace | Custom Medusa module | Вендори, vendor admins, зв’язок vendor–product–order, split orders |
| CMS | Payload CMS у Next.js repo або Medusa custom module | Stories, профілі, редакційні матеріали, сторінки партнерів |
| DB | PostgreSQL 16 | Основне сховище |
| Cache/queue | Redis + BullMQ | Кеш, черги, email, синхронізація доставок, payout reports |
| Files | Cloudflare R2 | Фото, документи, сертифікати, резервні копії |
| Video | Cloudflare Stream або Mux | Відео без навантаження на VPS |
| Edge/DNS/WAF | Cloudflare | TLS, CDN, rate limits, WAF, базовий DDoS protection |
| Deploy | Docker Compose, GitHub Actions, Hetzner CX31 | Достатньо для раннього production при винесених медіа/аналітиці |
| Monitoring | UptimeRobot/Better Stack + Sentry | Uptime, помилки, алерти |
| Email | Resend / Postmark / Brevo | Transactional email |
| Payments | LiqPay / Fondy / WayForPay — обрати один | Рішення залежить від юридичної особи, комісій і договору |
| Delivery | Nova Poshta API | Створення відправлень, статуси, розрахунок доставки, ТТН |

Medusa має офіційний приклад реалізації marketplace‑логіки через власний модуль: вендори й їхні адміністратори, прив’язка товарів і замовлень, а також групування товарів по вендорах для створення дочірніх замовлень. Це саме той рівень кастомізації, який потрібен для цього проєкту.[1]

Nova Post API підтримує створення відправлень, розрахунок вартості доставки, отримання статусів, друк документів та повернення за умовами сервісу; інтеграцію слід робити через ізольований adapter, а не виклики API безпосередньо з checkout.

### 10.6. Кошик і checkout

В MVP дозволено:

- Guest checkout.
- Вхід/реєстрація за email.
- Один кошик із товарами кількох вендорів.
- Розрахунок вартості доставки по кожній vendor shipment group.
- Оплата карткою через один provider.
- Оплата при отриманні — лише якщо це дозволяє vendor shipping profile.
- Створення parent order та дочірніх vendor orders.
- Email покупцю, вендору й адміністратору.
- Customer order page.
- Перегляд статусів доставки.

Мультивендорна логіка має групувати позиції кошика за вендором і формувати окремі vendor orders. Medusa документує подібний підхід через custom workflow та зв’язки між vendor, product і order.[1]

### 10.7. Доставка

Зробити інтерфейс `ShippingProviderAdapter`:

```ts
interface ShippingProviderAdapter {
  listPickupPoints(input): Promise<PickupPoint[]>
  calculate(input): Promise<ShippingQuote[]>
  createShipment(input): Promise<Shipment>
  getTracking(input): Promise<TrackingEvent[]>
  cancelShipment(input): Promise<void>
}
```

Реалізувати `NovaPoshtaAdapter`.

Функції першої версії:

- Вибір міста.
- Пошук відділення/поштомату.
- Доставка у відділення.
- Адресна доставка — за наявності даних від вендора.
- Розрахунок вартості.
- Створення відправлення після підтвердження замовлення.
- Збереження ТТН та shipment ID.
- Синхронізація статусів queue job-ом.
- Відображення трекінгу в кабінеті покупця.
- Вендор бачить тільки свої відправлення.

Nova Post API передбачає окремі операції для створення відправлення, редагування у статусі `ReadyToShip`, розрахунку ціни та отримання повного/скороченого трекінгу; adapter має мапити зовнішні статуси у внутрішню state machine.

### 10.8. Affiliate / referral module

#### Бізнес‑обмеження

- Комісія лише за **оплачені/успішно доставлені** замовлення.
- Джерело виплати — частина узгодженої маржі або marketing budget.
- Відсутні вступні внески.
- Відсутня винагорода за залучення партнерів як самоціль.
- MVP: один рівень атрибуції.
- Другий рівень може бути лише окремим майбутнім рішенням після юридичного погодження.
- Винагорода не нараховується на скасовані, повернені, fraud‑замовлення.

#### Сутності

```text
AffiliatePartner
AffiliateLink
AffiliateClick
Attribution
AffiliateConversion
CommissionRule
CommissionLedgerEntry
PayoutBatch
Payout
```

#### Логіка атрибуції

```text
1. Партнер отримує ref code: ?ref=alex-master
2. Система записує click_id, ref code, utm, landing page, IP hash, user-agent hash
3. Ставить first-party cookie на 30 днів
4. При checkout зберігає attribution у cart/order
5. Після статусу PAID або DELIVERED:
   - створити commission ledger entry зі статусом pending
6. Після завершення return window:
   - змінити статус на approved
7. Payout у MVP створюється вручну адміністратором
8. Після виплати: paid + payment reference
```

#### Правило атрибуції MVP

```text
Модель: last non-direct click
Вікно: 30 днів
Пріоритет: явний affiliate ref > збережений cookie > direct
Самореферал: заборонений
Кросдевайс: не гарантується у MVP
```

#### Кабінет афіліата

- Унікальне посилання.
- Можливість створити deeplink на конкретну сторінку.
- Кліки.
- Унікальні переходи.
- Замовлення в атрибуції.
- Pending / approved / paid commission.
- Експорт CSV.
- Платіжні реквізити.
- Умови програми.

### 11.2. Claim review

Для полів, що потенційно містять лікувальні, терапевтичні чи медичні твердження:


Правила:

- Не публікувати «лікує», «гарантує одужання», «цілющий», «реабілітує» без юридично й доказово погодженої підстави.
- Для категорій їжі відображати факти, а не оздоровчі обіцянки.
- Для медичних виробів зберігати документи та класифікацію.
- Для психологічних послуг додати disclaimer, що платформа не замінює екстрену медичну допомогу.
- Для роботи з травмою — окремий кризовий блок із контактами екстреної допомоги, які заповнює замовник.

Відомості про харчові продукти мають бути точними, зрозумілими й не вводити в оману, включно з інформацією про склад, алергени та інші обов’язкові дані.[2][3]

Реклама медичних послуг, лікарських засобів і медичних виробів має додаткові обмеження, тому медичні та лікувальні твердження мають проходити окремий review process.[4][5][6]

## 12. Нефункціональні вимоги

### Продуктивність

- LCP: до 2.5 с на mobile для основних сторінок у нормальній мережі.
- INP: до 200 мс як ціль.
- CLS: до 0.1.
- API p95: до 800 мс для типових read‑операцій.
- Checkout не повинен залежати від синхронного виклику зовнішнього API доставки після натискання «Оплатити».
- Зовнішні інтеграції мають retry policy та dead-letter логіку.

### Безпека

- TLS only.
- Secure, HttpOnly, SameSite cookies.
- Secrets лише через env/secret manager.
- Password hashing сучасним алгоритмом.
- RBAC.
- Rate limiting на auth, affiliate click endpoints і forms.
- CSRF protection там, де застосовно.
- Server-side validation через Zod.
- Upload allowlist: MIME, size, extension.
- Antivirus scan — post-MVP або через storage pipeline.
- Audit log для критичних адмін‑дій.
- Мінімізація PII.
- Не зберігати карткові дані.
- Резервні копії PostgreSQL зашифровані.

### Надійність

- Щоденний database backup у R2/S3.
- Retention: 30 днів.
- Перед кожною production migration — snapshot/backup.
- Health endpoints: `/healthz`, `/readyz`.
- Контейнерні `healthcheck`.
- Alerting на 5xx, disk > 80%, RAM > 85%, backup failure, queue failure.
- Docker log rotation.
- Один-два GB swap лише як аварійний buffer, а не постійна пам’ять.

### Accessibility

- Семантичний HTML.
- Keyboard navigation.
- Visible focus states.
- Контраст WCAG AA.
- Alt text.
- `prefers-reduced-motion`.
- Форми з помилками, що читабельні screen reader-ом.

### SEO

- SSR/ISR.
- `sitemap.xml`, `robots.txt`.
- Canonical URLs.
- Open Graph.
- JSON-LD: `Organization`, `Product`, `BreadcrumbList`, `Article`, `Event` — залежно від типу сторінки.
- Українські slug-и допускаються, але рекомендовано транслітеровані ASCII slug-и для стабільності URL.
- SEO metadata на рівні сторінки, категорії, товару, профілю та story.

## 14. API та інтеграційні правила

1. Всі інтеграції реалізуються через adapters/interfaces.
2. Немає provider-specific коду у UI або business workflows.
3. Webhooks мають бути idempotent.
4. Кожен зовнішній request має:
   - timeout;
   - retry для transient errors;
   - structured logging;
   - correlation ID;
   - failure status у БД або queue.
5. Секрети платіжного провайдера і Nova Poshta — тільки server-side.
6. Для sandbox і production використовувати окремі конфігурації та ключі.
7. Ніколи не блокувати checkout через довгі зовнішні процеси.

## 15. Acceptance criteria MVP

### Каталог

- Адмін створює категорію, вендора, профіль і товар.
- Товар після approval видно в каталозі, категорії та профілі вендора.
- Користувач знаходить товар пошуком або через категорію.
- Фільтри та сортування працюють.
- Товар має canonical URL, SEO title, description та OG‑image.

### Замовлення

- Гість додає товари одного або кількох вендорів у кошик.
- Система правильно групує позиції за вендором.
- Користувач обирає місто та пункт Нової пошти.
- Користувач завершує sandbox checkout.
- Створюються parent order та vendor orders.
- Вендор бачить тільки власну частину замовлення.
- Адмін бачить все замовлення та дочірні замовлення.
- Покупець і вендор отримують email‑повідомлення.
- Зберігається shipment ID / ТТН після створення відправлення.

### Affiliate

- Партнер отримує унікальне посилання.
- Клік зберігається без запису сирої IP‑адреси.
- Замовлення по лінку коректно отримує affiliate attribution.
- Після оплати комісія стає `pending`.
- Адмін може approve/reject комісію.
- Скасоване/повернене замовлення не може перейти у `paid`.
- Партнер бачить агреговану статистику і власний ledger.

### Контент

- Редактор створює story та прив’язує її до людини і товарів.
- Story коректно показується на storefront.
- Відео завантажується/відтворюється через зовнішній media provider.
- При `prefers-reduced-motion` декоративні анімації вимкнені або суттєво спрощені.

### Безпека та ops

- Усі production‑домени працюють через HTTPS.
- Production secrets не зберігаються у Git.
- Є перевірена процедура backup restore.
- Є staging environment.
- Є Sentry або еквівалент.
- Є uptime monitoring.
- CI не дозволяє merge при failure lint/typecheck/tests.

   - refunded/canceled order reversal;
   - suspicious click burst flags.

### Definition of Done

- Посилання `?ref=<code>` створює attribution.
- Зарахування комісії виконується рівно один раз.
- Комісія не стає payable, поки не закінчиться return window.
- Адмін бачить повний ledger.
- Партнер не бачить PII покупців.

# Важливі відкриті питання до замовника

Агент не має вирішувати це самостійно. Він має зібрати відповіді й зафіксувати у `docs/decisions`.

## Комерція

1. Хто є юридичним продавцем: платформа чи кожен вендор окремо?
2. Хто приймає оплату від покупця?
3. Хто видає чек/РРО?
4. Чи платформа утримує комісію, і яка її модель?
5. Чи buyer отримує одне замовлення/одну оплату при товарах різних вендорів?
6. Хто відповідає за повернення, гарантії та customer support?
7. Який payment provider обрано?
8. Чи підтримується післяплата, і хто несе ризик невидачі?

## Логістика

1. Кожен вендор сам відправляє товар чи існує один склад?
2. Чи має кожен вендор власний договір Нової пошти?
3. Хто платить за доставку?
4. Чи будуть доставка до відділення, поштомату, адресна доставка?
5. Чи будуть товари з температурними обмеженнями?
6. Чи можна поєднувати в одному кошику food і non-food?
7. Яка географія: тільки Україна чи також ЄС?

## Каталог

1. Які категорії реально запускаються в першій хвилі?
2. Які 10–20 виробників і майстрів готові надати дані першими?
3. Які категорії вимагають сертифікатів або документів?
4. Хто наповнює товарні картки й контент?
5. Хто модерує claims, документи й якість?
6. Чи «ЛАЙФ» — остаточна назва, і чи перевіряли ТМ/домен?

## Послуги та події

1. Чи послуги оплачуються на платформі чи лише через прямий контакт?
2. Онлайн, офлайн чи гібрид?
3. Чи потрібні календарі/слоти на старті?
4. Які правила скасування?
5. Хто несе відповідальність за послуги психологів/практиків?
6. Які документи/кваліфікації обов’язкові для фахівців?
7. Чи потрібні квитки, QR-коди та ліміти місць для подій?

## Affiliate

1. Хто може бути партнером: блогер, покупець, вендор, співробітник?
2. Який відсоток/сума комісії для кожної категорії?
3. Який return window?
4. Хто перевіряє й затверджує виплати?
5. Як афіліати надають реквізити?
6. Чи виплата раз на місяць, чи за досягнення мінімальної суми?
7. Чи потрібні промокоди на додаток до посилань?
8. Чи передбачається будь-який другий рівень? Якщо так — лише після юридичного висновку.
