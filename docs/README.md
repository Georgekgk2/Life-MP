# Документація «ЛАЙФ»

**Дата огляду структури:** 2026-08-21
**Поточний статус системи:** локальна розробка та контрольований sandbox; комерційний production — **не готовий і заблокований**.

Цей файл є головною картою документації. Він не замінює рішення або докази, на які посилається.

## Як читати документацію

1. Почніть із [кореневого README](../README.md), щоб зрозуміти локальний запуск.
2. Перед зміною функціонального scope прочитайте [межі запуску](decisions/launch-scope.md) та [реєстр відкритих рішень](decisions/open-questions.md).
3. Перед зміною архітектури прочитайте відповідні [ADR](adr/) і [огляд архітектури](architecture/overview.md).
4. Для локальних операцій використовуйте [посібник локальної розробки](runbooks/local-development.md), а не довільні команди з історичних нотаток.
5. Для тверджень про готовність використовуйте [ворота production readiness](decisions/production-readiness-gate.md). Локальні тести не є доказом production readiness.

## Ієрархія авторитетності

| Рівень | Джерело                         | Що воно підтверджує                                       | Чого воно не підтверджує                                          |
| ------ | ------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------- |
| 1      | Поточний код, міграції та тести | Фактичну поведінку конкретного commit/worktree            | Юридичне рішення, production-інфраструктуру або зовнішній договір |
| 2      | Прийнятий ADR                   | Архітектурний вибір і його межі                           | Наявність реалізації або дозвіл на запуск                         |
| 3      | Реєстр рішень                   | Статус зовнішнього рішення, власника та потрібного доказу | Мовчазне погодження незаповненого пункту                          |
| 4      | Архітектурні документи          | Модель, зв’язки та intended design                        | Факт увімкненої функції, якщо це не підтверджено кодом і тестом   |
| 5      | Runbook                         | Відтворювану локальну або дозволену операційну процедуру  | Дозвіл виконувати заборонені або production-дії                   |
| 6      | `TZ.txt`, плани та чернетки     | Вимоги, гіпотези та майбутні варіанти                     | Реалізацію, підписання чи готовність                              |

Якщо джерела суперечать одне одному, діє безпечний дефолт: функція не вмикається, а суперечність реєструється в рішенні.

## Статуси доказів

- **Реалізовано** — шлях або модуль існує в поточному коді.
- **Перевірено** — для конкретного твердження є прямий результат поточної команди або тесту.
- **Частково підтверджено** — є локальний або неповний доказ, але відсутня незалежна чи production-перевірка.
- **Заплановано** — описано майбутню роботу, якої немає в поточному коді.
- **Відкладено** — свідомо не вмикається в поточному scope.
- **Заблоковано** — перехід неможливий до появи визначеного рішення або доказу.
- **Не перевірено** — доказу в поточній сесії або для поточного commit немає.

Слова «готово», «стабілізовано» та «підтверджено» завжди мають бути прив’язані до конкретного обсягу, commit, команди, дати та результату.

## Правила оновлення

Кожна зміна документації повинна:

1. вказувати обсяг, дату огляду та власника;
2. розділяти факт, рішення, припущення й відкритий блокер;
3. посилатися на код, тест, commit або зовнішній артефакт, якщо заявляє доказ;
4. не створювати дозвіл на production через сам факт написання документа;
5. оновлювати всі залежні посилання та реєстр документації;
6. проходити `pnpm docs:check`.

Не зберігайте секрети, персональні дані покупців, реальні документи вендорів або бойові ключі в документації.
