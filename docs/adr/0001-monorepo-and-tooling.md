# ADR 0001 — Монорепозиторій та базові інструменти

- **Дата:** 2026-07-27
- **Власник ADR:** технічний власник Life-MP
- **Межі:** це рішення фіксує цільову технічну основу; воно не підтверджує, що конфігурація вже існує або розгорнута.

## Контекст

[ТЗ](../../TZ.txt) описує структуру з `apps/` і `packages/`, а також окремі storefront і commerce-компоненти. У поточному локальному середовищі спостережено Node.js 22.22.3 і pnpm 11.4.0. На підставі цієї структури та спостереженого середовища цей ADR обирає `pnpm workspaces` і Node.js 22 як стандарт репозиторію.

Якість джерел: версії Node.js 22.22.3 і pnpm 11.4.0 є спостереженими локальними інструментами, а не прямими вимогами користувача. `pnpm workspaces` і Node.js 22 є технічним рішенням цього ADR; ТЗ є плановим технічним джерелом. Жодне з них не є підтвердженням клієнтського, юридичного або інфраструктурного схвалення.

## Рішення

Використовувати один монорепозиторій на `pnpm workspaces` з Node.js 22 для локальної розробки та CI. Кореневими межами робочих просторів будуть `apps/*` і `packages/*`; конкретний склад пакетів визначається лише тоді, коли з'являється реальний код.

Цей ADR не вводить commerce-функціональність, не обирає CI-провайдера та не створює конфігураційних файлів.

## Наслідки

- Спільні типи, UI та конфігурації можуть мати один контрольований власний пакет замість копій між застосунками.
- Версію Node.js 22 і `pnpm` потрібно явно фіксувати в майбутніх локальних та CI-конфігураціях, щоб уникнути різних середовищ виконання.
- Додавання workspace без коду або без визначеного власника не є метою цього рішення.
- Перехід на інший менеджер пакетів або runtime вимагатиме нового ADR, а не паралельного використання кількох інструментів.

## Приймання

Рішення буде реалізовано коректно, коли одночасно виконано такі умови:

1. кореневий manifest явно описує `pnpm workspaces` для `apps/*` і `packages/*`;
2. локальний та CI runtime явно вказують Node.js 22;
3. нові внутрішні залежності використовують workspace-посилання, а не дублюють спільний код;
4. зміна не додає commerce-функціональності лише заради інструментів.

Ці умови є критеріями майбутньої реалізації, а не заявою про їхнє поточне виконання.

## Відкат

Якщо практичне впровадження виявить несумісність, технічний власник має замінити цей ADR новим рішенням і виконати один контрольований перехід. Не допускається тихо підтримувати одночасно кілька менеджерів пакетів або кілька версій runtime як «відкат».
