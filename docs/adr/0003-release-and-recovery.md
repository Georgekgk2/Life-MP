# ADR 0003 — Релізи та відновлення

- **Дата:** 2026-07-27
- **Власник ADR:** технічний власник Life-MP
- **Межі:** це рішення визначає модель promotion і штатного rollback; воно не підтверджує налаштований захист гілок, реєстр образів або перевірений runbook.

## Контекст

[ТЗ](../../TZ.txt) пов'язує `main` з production, вимагає Pull Request, незмінні tagged Docker images, backup перед migration і rollback runbook. На підставі цих delivery/recovery-орієнтирів, попереднього evidence-bound планування та вимог безпеки цей ADR приймає захищений головний trunk, immutable promotion і штатний rollback образом замість відновлення БД.

Якість джерел: модель release і recovery є архітектурним рішенням цього ADR, мотивованим ТЗ, попереднім evidence-bound плануванням і вимогами безпеки. ТЗ є плановим описом delivery та recovery. ТЗ згадує backup/restore drill, але не є доказом існування backup або дозволом використовувати restore як звичайний релізний rollback.

## Рішення

`main` є захищеним production trunk: до нього не допускаються прямі або примусові зміни поза затвердженою policy гілки. Точні вимоги review та перевірок не визначаються цим ADR.

Promotion виконується одним і тим самим уже зібраним незмінним image, ідентифікованим незмінним reference (зокрема digest). Production не перебудовує та не підміняє образ під час promotion.

Штатний rollback релізу — повторне розгортання попереднього відомо справного незмінного image. Перед релізом migration має бути сумісною з таким rollback або мати окремий схвалений операційний план.

**Відхилено:** звичайне відновлення бази даних не є механізмом rollback релізу. Emergency-відновлення після доведеної втрати чи пошкодження даних лишається окремою incident-процедурою; цей ADR її не авторизує і не скасовує потребу у backup/restore drill.

## Наслідки

- Promotion стає відтворюваним: production отримує саме той image, що вже був підготовлений для promotion.
- Штатний rollback не перезаписує дані заради відкату коду, тому міграції потребують явної сумісності або окремого плану.
- Backup залишається потрібним для аварійного відновлення, але не маскує помилки релізного процесу.
- Реальні branch policy, image immutability і rollback runbook ще треба налаштувати; документ не є доказом їхньої наявності.

## Приймання

Рішення буде реалізовано коректно, коли одночасно виконано такі умови:

1. policy `main` забороняє прямі та force-оновлення і документує дозволений шлях promotion;
2. production deploy посилається на вже зібраний immutable image reference, а не створює новий image;
3. runbook штатного rollback повторно розгортає попередній known-good image та не містить database restore як крок релізного rollback;
4. для кожної migration до promotion зафіксовано сумісність з image rollback або окремий операційний план;
5. emergency restore описано окремо від release rollback і не виконується як стандартна реакція на невдалий реліз.

Ці умови є критеріями майбутньої реалізації, а не заявою про їхнє поточне виконання.

## Відкат

Для штатного релізного відкату зупинити promotion і повторно розгорнути попередній known-good immutable image, після чого перевірити визначені health-сигнали. **Не відновлювати БД як нормальний rollback.** Якщо є ознаки втрати або пошкодження даних, перейти до окремого incident-процесу з явним рішенням про emergency restore; це не є fallback для release workflow.
