# ADR 0004 — Ізоляція production від Jorvis

- **Дата:** 2026-07-27
- **Власник ADR:** технічний власник Life-MP
- **Межі:** цей ADR встановлює обов'язкову межу Life-MP production. Назва Jorvis використовується як визначений у поточному плануванні окремий контур; поточний інвентар Jorvis або Life-MP не перевірено.

## Контекст

[ТЗ](../../TZ.txt) містить лише планові орієнтири для раннього production і прямо вимагає load test перед корекцією лімітів. На підставі цього контексту, попереднього evidence-bound планування та вимог безпеки й ізоляції цей ADR відокремлює Life-MP production від credential, backup і network ресурсів Jorvis та запроваджує gate інвентаризації сервера.

Якість джерел: межа ізоляції та server-discovery gate є технічними рішеннями цього ADR, мотивованими ТЗ, попереднім evidence-bound плануванням і вимогами безпеки та ізоляції. ТЗ є плановим технічним джерелом місткості, а не доказом наявного сервера, мережі, облікових даних, backup-контурів або права їх використовувати. Не робиться висновок, що будь-який Jorvis ресурс взагалі доступний.

## Рішення

Life-MP production має мати незалежні від Jorvis:

- облікові дані, секрети, ключі та контури їх ротації;
- цілі резервного копіювання, ключі шифрування та доступ до backup;
- мережеві межі, ingress/egress policy і адміністративний доступ.

**Відхилено:** повторне використання будь-яких Jorvis credential, backup або network ресурсів для Life-MP production, у тому числі як тимчасовий fallback.

До будь-якого production provisioning діє server-discovery gate. Він має зафіксувати без розкриття секретів: власника й межі compute/storage, мережеву topology та доступи, scope облікових даних, backup-контур, а також доступну місткість проти погодженого MVP профілю. Production не може бути створено або promoted, доки gate та профільний load test не дадуть достатніх доказів.

## Наслідки

- Міжпроєктний blast radius для доступів, мережі та відновлення зменшується.
- Ізоляція не дозволяє використати Jorvis як аварійний ресурс, тож capacity і backup-контур Life-MP потрібно планувати самостійно.
- Планові орієнтири ТЗ не є підставою виділяти сервер або заявляти, що він витримає MVP.
- Цей ADR не створює інфраструктуру, не сканує сервери й не надає доступу до будь-якого ресурсу.

### Розділення станів доказів

| Стан | Межа твердження |
|---|---|
| **Confirmed** | Цей ADR встановлює межу ізоляції та server-discovery gate; ТЗ вказує, що capacity-ліміти є лише орієнтирами. |
| **Provisional** | Конкретний провайдер, topology сегментації, розмір ресурсу й спосіб backup ще не обрані. |
| **Unanswered** | Немає перевірених даних про сервер, мережу, обсяг, I/O, адміністраторів, backup або доступні ресурси. |
| **Deferred** | Деталі provisioning, monitoring і migration реалізовуються лише після проходження gate. |
| **Blocked** | Production provisioning та окремий Payload-сервіс не можуть рухатися без інвентаризації й профільного load test. |

## Приймання

Ізоляцію та gate можна вважати реалізованими лише коли одночасно виконано такі умови:

1. технічний інвентар описує compute, storage, мережу, адміністраторів і межі доступу Life-MP без значень секретів;
2. доказ доступів показує, що Life-MP не використовує Jorvis credential, backup-цілі/ключі або мережеві сегменти;
3. Life-MP backup-контур і ключі мають окремий scope та власника;
4. профільний load test порівнює доступну місткість із погодженим MVP профілем без OOM або непогодженого виснаження ресурсу;
5. до виконання попередніх умов немає production promotion.

Ці умови є критеріями майбутньої реалізації, а не заявою про їхнє поточне виконання.

## Відкат

Немає допустимого rollback до спільних Jorvis ресурсів. Якщо виявлено спільний credential, backup або network path, affected production exposure треба зупинити або ізолювати до відновлення незалежної межі; не слід переводити Life-MP на Jorvis як тимчасове рішення. Будь-яка інша topology потребує нового ADR і повторного проходження discovery gate.
