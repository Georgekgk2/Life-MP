# ADR 0005 — Пошук MVP і умовний внутрішній Payload

- **Дата:** 2026-07-27
- **Власник ADR:** технічний власник Life-MP
- **Межі:** цей ADR не розгортає пошук або CMS та не підтверджує місткість сервера, результати load test чи вибір CMS для production.

## Контекст

[ТЗ](../../TZ.txt) вимагає full-text search для каталогу, редакційний CMS-модуль, забороняє постійне розгортання Meilisearch/Typesense на запланованому ранньому сервері та називає його ліміти лише орієнтирами до load test. ТЗ також залишає Payload у Next.js або Medusa content module як відкритий вибір. На підставі цих потреб і обмежень, попереднього evidence-bound планування та вимог ізоляції цей ADR обирає PostgreSQL FTS/trigram для MVP і допускає окремий внутрішній Payload-сервіс лише за наявності capacity та load-test доказів.

Якість джерел: стратегія MVP-пошуку та умови для Payload є архітектурними рішеннями цього ADR, мотивованими ТЗ, попереднім evidence-bound плануванням і вимогами безпеки та ізоляції. ТЗ є плановим джерелом функціональної потреби та обмежень, але не доказом catalog-навантаження, редакційного навантаження, поточного сервера або production readiness.

## Рішення

Для MVP пошук каталогу реалізовується в PostgreSQL через full-text search і `pg_trgm`. Окремий пошуковий сервіс для MVP не розгортається.

Окремий внутрішній Payload-сервіс є кандидатом, а не прийнятим production-рішенням. Його можна розгортати лише після виконання server-discovery gate з [ADR 0004](0004-production-isolation.md) і профільного load test, який підтвердить погоджену місткість для базових сервісів плюс Payload. До цього він не отримує production promotion і не має публічного клієнтського ingress.

Цей ADR не вибирає мову FTS-конфігурації, набір полів, Payload-версію, CMS-модель поза вказаною умовою або зовнішній пошуковий рушій.

## Наслідки

- MVP уникає додаткового постійного пошукового сервісу та використовує вже обрану PostgreSQL-поверхню.
- FTS і триграмні індекси потребують вимірювання на фактичному catalog-профілі; їх не можна вважати безкоштовними за CPU, RAM чи I/O.
- Окремий Payload потребує власних resource limits, внутрішньої мережевої межі та окремої бази/ролі за [ADR 0002](0002-data-boundaries.md), якщо буде схвалений.
- Невдалий capacity або load test не виправдовує неявний deployment Payload або аварійне додавання зовнішнього пошуку.

### Розділення станів доказів

| Стан | Межа твердження |
|---|---|
| **Confirmed** | Цей ADR встановлює PostgreSQL FTS/trigram для MVP; ТЗ вимагає full-text search і CMS-модуль. |
| **Provisional** | Внутрішній Payload-сервіс, його resource limits і deployment topology лишаються умовними. |
| **Unanswered** | Немає підтверджених обсягу каталогу, query mix, редакційної конкуренції, SLO або критеріїв успішності load test. |
| **Deferred** | Dedicated search, публічний Payload ingress і детальна CMS-модель не є рішеннями MVP цього ADR. |
| **Blocked** | Payload production deployment заблокований до проходження server discovery та профільного load test. |

## Приймання

### PostgreSQL FTS + `pg_trgm`

Рішення буде реалізовано коректно, коли пошук каталогу використовує FTS і триграмні індекси для погоджених полів, а deployment не додає окремий пошуковий сервіс для MVP. Результат потрібно виміряти на погодженому catalog-профілі; цей ADR не заявляє про таке вимірювання зараз.

### Окремий внутрішній Payload-сервіс

Payload може бути прийнятий до production лише коли одночасно виконано такі умови:

1. server-discovery gate з ADR 0004 задокументований і не виявляє спільних Jorvis ресурсів;
2. профільний load test покриває базові сервіси та Payload на погодженому MVP профілі без непогодженого виснаження ресурсу;
3. Payload має внутрішню мережеву межу, власні resource limits і окрему базу/роль відповідно до ADR 0002;
4. немає публічного клієнтського ingress до Payload без окремого ADR.

До виконання цих умов статус Payload лишається **Proposed / Blocked**, а не Accepted.

## Відкат

Для пошуку штатний відкат повертає попередню відому справну реалізацію каталогу або прибирає проблемну зміну індексу; він не додає dedicated search як аварійний обхід. Якщо Payload не проходить capacity або load test, його не просувають у production або знімають з promotion без fallback на shared Jorvis ресурси. Релізний rollback образу виконується за [ADR 0003](0003-release-and-recovery.md), а не нормальним database restore.
