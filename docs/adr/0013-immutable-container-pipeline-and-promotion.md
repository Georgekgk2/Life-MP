# ADR 0013 — Незмінний конвеєр збірки контейнерів та протокол промоції GHCR (Фаза P2)

- **Дата:** 2026-09-10
- **Власник ADR:** технічний та інфраструктурний власник Life-MP
- **Статус:** Accepted (Прийнятий архітектурний дизайн; реалізація виконується поетапно)

## Контекст

1. **Проблема локальної збірки на спільному хості:**
   Згідно з [ADR 0004](0004-production-isolation.md), продакшн-середовище Life-MP розміщено на спільному сервері (`34.139.21.224`, 2 CPU, обмеження RAM до 2 ГБ для Life-MP), де також функціонують сервіси Jorvis.
   Поточна конфігурація `deploy/docker-compose.prod.yml` містить директиви `build:`, що вимагає компіляції важких додатків (Next.js 16 та Medusa v2) безпосередньо на цільовому хості під час кожного запуску. Це призводить до:
   - пікових стрибків споживання пам'яті (ризик Out-Of-Memory та взаємного впливу з Jorvis);
   - присутності вихідного коду, компіляторів та розробницьких `node_modules` на хості;
   - відсутності гарантії повної байтової ідентичності зібраних образів між середовищами;
   - порушення принципу незмінної інфраструктури ([ADR 0003](0003-release-and-recovery.md)).

2. **Вимоги безпеки ланцюга постачання (Supply-Chain Security):**
   - Перенесення збірки на безкоштовні ізольовані раннери GitHub Actions (`ubuntu-latest`);
   - Запобігання атакам класу TOCTOU (Time-of-Check to Time-of-Use), коли сканується один білд образу, а в реєстр відправляється інший;
   - Суворе дотримання політики ізоляції (Phase P0/P2 Containment) без надання репозиторію прав неконтрольованого віддаленого деплою.

## Рішення

### 1. Модель єдиного артефакту (Single-Artifact Pipeline: Build ➔ Scan ➔ Push)

Для виключення повторної збірки та гарантії того, що публікується саме той образ, який пройшов аудит безпеки, впроваджується суворий конвеєр:

1. **Збірка:** Docker BuildKit збирає образ виключно під цільову архітектуру хоста `linux/amd64` і експортує його в єдиний локальний OCI/Docker архів:
   `--output type=docker,dest=/tmp/image.tar`.
2. **Сканування:** Сканер безпеки Trivy (`aquasecurity/trivy-action`, зафіксований за незмінним commit SHA) перевіряє безпосередньо збережений архівний файл:
   `input: /tmp/image.tar`.
3. **Політика вразливостей:** Встановлюється fail-closed поріг `severity: "CRITICAL,HIGH"`. Дозволені винятки регламентуються виключно через перевірений файл `.trivyignore`, де кожен запис має задокументовану причину та дату обов'язкового перегляду. Вразливості без виправлення (`ignore-unfixed: true`) відстежуються в реєстрі залишкових ризиків.
4. **Завантаження та Публікація:** Лише за умови нульових критичних знахідок виконується завантаження артефакту в локальний Docker-демон раннера (`docker load -i /tmp/image.tar`) і відправка в GitHub Container Registry (`ghcr.io/georgekgk2/life-commerce` та `life-storefront`) під тегом `sha-<github_sha>`.
5. **Фіксація дайджесту та атестація:** З реєстру отримується канонічний `sha256`-хеш образу (digest), генерується звіт `IMAGE_DIGESTS.json`, і за допомогою `actions/attest-build-provenance` створюється підписана provenance-атестація збірки.

### 2. Модель тригерів, дозволів та раннерів у GitHub Actions

- **Тригер:** Виключно `push: branches: [main]` (post-merge). Запуск на подію `pull_request` суворо заборонено, що виключає доступ неперевіреного коду із форків чи робочих гілок до прав публікації.
- **Мінімальні права (Least Privilege):** Дозвіл `packages: write` надається ізольовано на рівні конкретної джоби публікації (`publish`), а не глобально на весь workflow.
- **Аутентифікація:** Використовується виключно автоматичний короткоживучий `GITHUB_TOKEN`, жодних персональних токенів доступу (PAT) або постійних секретів.
- **Ізоляція раннерів:** Збірка виконується суворо на хмарних раннерах GitHub (`ubuntu-latest`), без використання self-hosted раннерів на хості `34.139.21.224`.

### 3. Фазове розмежування політики репозиторію (Фаза P0 ➔ Фаза P2)

Поточна політика Phase P0 (`infra/deployment-policy.json`) блокує будь-які дії з публікації. Перехід до Фази P2 регламентується через контрольоване розширення:

- Гейт `allow_ghcr_image_push` переводиться в стан `true` **виключно для канонічного workflow публікації** на `main`;
- Сканер `deployment-containment.ts` оновлюється з підтримкою перевірки:
  - публікація дозволена лише у визначені репозиторії (`ghcr.io/georgekgk2/life-*`);
  - заборонені будь-які прямі SSH-дії, `appleboy/ssh-action`, секрети хоста (`DEPLOY_SSH_KEY`);
  - комерційні гейти (`allow_live_payment_gateway`, `allow_live_shipping_api`, `allow_live_fiscalization`) залишаються заблокованими (`false`).

### 4. Розділення публікації (P2a) та промоції (P2b)

Процес розгортання чітко розмежовується на два незалежних етапи:

- **P2a (CI Registry Publication):** Автоматична збірка та публікація образів за результатами злиття коммітів у `main`. Не спричиняє жодних автоматичних змін на сервері чи в репозиторії.
- **P2b (Explicit Digest Promotion):** Окремий узгоджений PR, який оновлює `deploy/docker-compose.prod.yml`:
  1. Видаляє блоки `build:`;
  2. Замінює плаваючі теги додатків на точні immutable digests:
     `ghcr.io/georgekgk2/life-storefront@sha256:...` та `ghcr.io/georgekgk2/life-commerce@sha256:...`;
  3. Фіксує точні digests для сервісних образів: `postgres:16-alpine@sha256:...` та `redis:7-alpine@sha256:...`;
  4. Перевіряє коректність конфігурації через `docker compose config`.

### 5. Заборона автоматичного оновлення продакшну

- Жоден скрипт чи крок CI не виконує автоматичний `docker compose pull` або `up` на хості `34.139.21.224`.
- Оновлення контейнерів на сервері залишається явною, авторизованою дією оператора, яка полягає виключно у завантаженні попередньо протестованих та зафіксованих образів за дайджестом, без виконання збірки на хості.

## Наслідки

- **Безпека хоста:** Усувається пікове навантаження CPU та RAM під час релізів; на сервері відсутні компілятори, сирцеві коди та кеші збірки.
- **Ідентичність:** Образи збираються один раз у детермінованому хмарному середовищі та супроводжуються криптографічною атестацією походження.
- **Reproducibility Caveat:** Інструкція `RUN apk upgrade --no-cache` у Dockerfile оновлює системні пакети Alpine під час збірки. Точний снепшот зафіксовано результуючим `sha256`-хешем образу в GHCR, що забезпечує ідемпотентність розгортання після публікації.
- **Ізоляція від Jorvis:** Повністю відповідає вимогам [ADR 0004](0004-production-isolation.md) щодо нульового впливу на ресурси та пам'ять сусідніх проєктів.

## Приймання

Фазу P2 можна вважати завершеною лише за умови виконання наступних критеріїв:

1. Створено та верифіковано автономний workflow `.github/workflows/release-images.yml` із ланцюжком Single-Artifact (tar ➔ Trivy ➔ GHCR);
2. Сканер безпеки `deployment-containment.ts` оновлено з підтримкою дозволеної GHCR-публікації на `main` та покрито unit-тестами;
3. У репозиторії згенеровано та збережено артефакт `IMAGE_DIGESTS.json`;
4. `deploy/docker-compose.prod.yml` очищено від секцій `build:` та переведено на незмінні дайджести;
5. Кожен PR проходить повноцінний незалежний review відповідно до політики репозиторію.

## Відкат

Якщо публікація в GHCR або завантаження образів за дайджестом зазнає невдачі, сервіси на хості продовжують функціонувати на діючому релізі `public-demo` (`rel-20260909T153926Z-57d00ac`). Повернення до збірки на продакшн-сервері заборонено.
