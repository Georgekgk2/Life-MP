# ADR 0014 — Архітектура тестового платіжного шлюзу (Payment Gateway Sandbox)

- **Статус:** `Прийнято` (як архітектурне рішення для тестового контуру пісочниці)
- **Дата:** 2026-09-11
- **Власник:** технічний власник Life-MP + фінансовий архітектор
- **Межа:** це рішення визначає технічний контракт та архітектуру модуля тестового еквайрингу для Medusa v2 у режимі пісочниці (`sandbox-only`). Воно **не авторизує** підключення бойових банківських ключів, не є дозволом на здійснення реальних фінансових розрахунків і не скасовує блокування комерційних гейтів (`COM-1`, `COM-2`, `COM-3`, `COM-5`).
- **Замінює / замінено:** Немає. Розширює [ADR 0010](0010-multi-vendor-checkout-and-order-splitting.md) та узгоджується з [ADR 0004](0004-production-isolation.md).

---

## 1. Контекст

Маркетплейс локальних ремісничих виробів потребує безготівкового прийому платежів із підтримкою сучасних методів оплати (Apple Pay, Google Pay, банківські картки) та механізму захищених угод (Escrow/Hold) для мультивендорного кошика ([ADR 0010](0010-multi-vendor-checkout-and-order-splitting.md)).

На поточному етапі комерційний запуск залишається заблокованим (`STRICT NO-GO / PENDING` згідно з [Phase 5 Decision Pack](../decisions/phase5-commercial-activation-decision-pack.md)), оскільки тривають юридичні та податкові погодження моделі продавця (`COM-1`) та оператора коштів (`COM-2`). 

Проте для завершення технічного циклу розробки вітрини та перевірки наскрізного процесу оформлення замовлення (End-to-End Checkout) необхідна повноцінна, безпечна і криптографічно захищена архітектура платіжного адаптера в тестовому режимі.

---

## 2. Рішення

### 2.1. Вибір цільового провайдера пісочниці
Для реалізації тестового еквайрингу обрано **Monobank Acquiring Sandbox API**:
- Сучасний RESTful/JSON протокол взаємодії;
- Нативна підтримка одностадійних платежів (`debit`) та двостадійного холдування (`hold`) для реалізації Escrow-механізму;
- Підтримка Apple Pay / Google Pay безпосередньо у платіжному вікні;
- Вбудована криптографічна автентифікація вебхуків на основі асиметричного підпису ECDSA.

### 2.2. Архітектура модуля в Medusa v2
Створюється ізольований модуль платіжного провайдера `@life/medusa-payment-monobank`, який наслідує стандартний `AbstractPaymentProvider` платформи Medusa v2:

```text
Покупець (Storefront)
      │
      ▼  (1. Ініціалізація чекауту)
Commerce API (Medusa v2 Workflow)
      │
      ▼  (2. POST /api/merchant/invoice/create)
Monobank Sandbox API
      │
      ▼  (3. Отримання pageUrl та invoiceId)
Покупець перенаправляється на сторінку оплати (Sandbox)
      │
      ▼  (4. Тестова оплата карткою)
Monobank генерує ECDSA підпис (X-Sign)
      │
      ▼  (5. POST /api/hooks/payment/monobank)
Webhook Handler (Commerce API)
      ├── Валідація підпису ECDSA через публічний ключ банку
      ├── Перевірка ідемпотентності за invoiceId (Redis Mutex)
      └── Зміна статусу: Payment Authorized (Hold) / Payment Captured
```

### 2.3. Криптографічна безпека вебхуків (Fail-Closed Verification)
1. **Асиметричний підпис ECDSA:**  
   Кожен зворотний виклик (webhook) від банку супроводжується HTTP-заголовком `X-Sign`, що містить підпис тіла запиту, згенерований приватним ключем банку.
2. **Отримання та кешування публічного ключа:**  
   Публічний ключ банку запитується через захищений ендпоінт `GET /api/merchant/pubkey` і кешується у Redis із часом життя (TTL) 24 години.
3. **Принцип відмови за замовчуванням (Fail-Closed):**  
   Якщо заголовок `X-Sign` відсутній, підпис не збігається з тілом запиту або публічний ключ недоступний — обробник **негайно повертає `HTTP 401 Unauthorized`**. Жодних змін стану замовлення чи бази даних не виконується.

### 2.4. Захист від повторних атак та ідемпотентність (Replay Protection)
1. **Унікальний індекс транзакції:**  
   Кожен `invoiceId` прив'язується до платіжної сесії Medusa v2 унікальним індексом у базі даних.
2. **Розподілений лок (Distributed Mutex):**  
   Під час обробки вхідного вебхука встановлюється короткоживучий ключ у Redis: `lock:payment:monobank:{invoiceId}` на 10 секунд. Повторні паралельні запити відхиляються або очікують завершення першої транзакції.
3. **Ідемпотентний статус:**  
   Якщо замовлення вже перебуває в статусі `authorized` або `captured`, повторний вебхук логується як дублікат і повертає `HTTP 200 OK` без повторного виклику бізнес-подій.

### 2.5. Модель двостадійного холдування (Escrow Hold)
Згідно з [ADR 0010](0010-multi-vendor-checkout-and-order-splitting.md), платежі за замовчуванням ініціюються з параметром `paymentType: "hold"`:
- Кошти покупця резервуються (блокуються) на термін до 7 днів;
- Фінальне списання (`capture`) ініціюється автоматично лише після того, як ремісник підтвердить прийом замовлення у виробництво;
- У разі відмови майстра від виконання замовлення холд скасовується (`void/cancel`) миттєво та без комісій за еквайринг для покупця.

## 3. Наслідки

### Позитивні
- Повна готовність коду вітрини та бекенду до прийому платежів у безпечному тестовому середовищі;
- Наскрізне тестування поведінки інтерфейсу (успішна оплата, відхилення карти, 3D-Secure, повернення в кошик);
- Надійний захист від фейкових запитів про оплату завдяки обов'язковій верифікації ECDSA-підписів;
- Архітектурна ізоляція модуля: заміна або додавання іншого платіжного провайдера (наприклад, LiqPay) у майбутньому не вимагатиме переписування ядра комерції.

### Негативні та ризики
- Необхідність підтримки кешування та ротації публічного ключа банку;
- Залежність тестового середовища від стабільності зовнішнього sandbox-сервера банку (компенсується наявністю локального мока для CI).

### Що залишається суворо заблокованим
- **`allow_live_payment_gateway: false`** у файлі політики `infra/deployment-policy.json` залишається у заблокованому стані;
- Заборонено внесення бойових токенів еквайрингу до конфігурацій чи секретів хоста;
- Будь-які фінансові розрахунки на живому сайті `https://life-mp.pp.ua/` залишаються суворо вимкненими до окремого підписаного рішення власників.

| Критерій | Необхідний доказ | Поточний статус | Відповідальний |

## 5. Безпека та приватність

1. **Мінімізація PII (Персональних даних):**  
   Платіжний модуль не зберігає і не логує номери банківських карток, терміни дії або CVV/CVC-коди. Уся взаємодія з даними платіжних карток відбувається виключно на захищеній PCI-DSS сумісній платіжній сторінці банку.
2. **Кореляційне логування (Audit Logs):**  
   Усі платіжні події логуються із санітизованими метаданими: `timestamp`, `orderId`, `invoiceId`, `status`, `durationMs`. Будь-які секретні ключі, токени та повні імена покупців фільтруються перед записом у лог.
3. **Ізоляція ключів:**  
   Тестові токени передаються виключно через змінні середовища `MONOBANK_SANDBOX_TOKEN` у локальному файлі `.env.local` (який знаходиться в `.gitignore`).

---

## 6. Відкат або заміна

Якщо інтеграція з Monobank Sandbox буде відхилена замовником на користь іншого провайдера (наприклад, LiqPay або NovaPay):
1. Модуль `@life/medusa-payment-monobank` вимикається в конфігурації `medusa-config.ts` перемиканням однієї змінної;
2. Реалізується аналогічний адаптер для нового провайдера за цим самим інтерфейсом `AbstractPaymentProvider`;
3. Жодних міграцій бази даних чи руйнування історії замовлень не відбувається завдяки поліморфній структурі платіжних сесій Medusa v2.
