# ADR 0014 — Архітектура тестового платіжного шлюзу (Payment Gateway Sandbox)

- **Статус:** `Прийнято` (як архітектурне рішення для тестового контуру пісочниці)
- **Дата:** 2026-09-11
- **Власник:** технічний власник Life-MP + фінансовий архітектор
- **Межа:** це рішення визначає технічний контракт та архітектуру модуля тестового еквайрингу для Medusa v2 у режимі пісочниці (`sandbox-only`). Воно **не авторизує** підключення бойових банківських ключів, не є дозволом на здійснення реальних фінансових розрахунків і не скасовує блокування комерційних гейтів (`COM-1`, `COM-2`, `COM-3`, `COM-5`).
- **Замінює / замінено:** Немає. Розширює [ADR 0010](0010-multi-vendor-checkout-and-order-splitting.md) та узгоджується з [ADR 0004](0004-production-isolation.md).

---

## 1. Контекст

Маркетплейс локальних виробів потребує безготівкового прийому платежів із підтримкою двостадійного холдування коштів для безпечної мультивендорної моделі ([ADR 0010](0010-multi-vendor-checkout-and-order-splitting.md)).

На поточному етапі комерційний запуск залишається заблокованим (`STRICT NO-GO / PENDING` згідно з [Phase 5 Decision Pack](../decisions/phase5-commercial-activation-decision-pack.md)), оскільки тривають юридичні та податкові погодження моделі продавця (`COM-1`) та оператора коштів (`COM-2`).

Для завершення технічного циклу розробки вітрини та перевірки наскрізного процесу оформлення замовлення (End-to-End Checkout) необхідна повноцінна, безпечна і криптографічно захищена архітектура платіжного адаптера в тестовому режимі.

---

## 2. Рішення

### 2.1. Вибір цільового провайдера пісочниці

Для реалізації тестового еквайрингу обрано **Monobank Acquiring Sandbox API**:

- Сучасний RESTful/JSON протокол взаємодії;
- Нативна підтримка одностадійних платежів (`debit`) та двостадійного холдування (`hold`);
- Вбудована криптографічна автентифікація вебхуків на основі асиметричного підпису ECDSA.

### 2.2. Архітектура модуля в Medusa v2

Створюється ізольований модуль платіжного провайдера `@life/medusa-payment-monobank`, який наслідує стандартний `AbstractPaymentProvider` платформи Medusa v2:

```text
Покупець (Storefront)
      │
      ▼  (1. Ініціалізація чекауту)
Commerce API (Medusa v2 Workflow)
      │
      ▼  (2. POST /api/merchant/invoice/create)
Monobank Sandbox API
      │
      ▼  (3. Отримання pageUrl та invoiceId)
Покупець перенаправляється на сторінку оплати (Sandbox)
      │
      ▼  (4. Тестова оплата карткою)
Monobank генерує ECDSA підпис (X-Sign)
      │
      ▼  (5. POST /api/hooks/payment/monobank)
Webhook Handler (Commerce API)
      ├── Валідація підпису ECDSA через публічний ключ банку (з forced cache-refresh)
      ├── Перевірка ідемпотентності (PostgreSQL durable ledger + Redis Mutex)
      ├── Валідація суми, валюти (UAH 980) та перевірка допустимих FSM-переходів
      └── Зміна статусу: Payment Authorized (Hold) / Payment Captured
```

### 2.3. Криптографічна безпека вебхуків та ротація публічного ключа (Fail-Closed)

1. **Асиметричний підпис ECDSA:**  
   Кожен зворотний виклик (webhook) від банку супроводжується HTTP-заголовком `X-Sign`, що містить підпис сирого бінарного тіла запиту (raw request body), згенерований приватним ключем банку за алгоритмом ECDSA з SHA-256.
2. **Кешування з форсованим оновленням (Forced Cache-Busting):**
   - У штатному режимі публічний ключ банку запитується через `GET /api/merchant/pubkey` і кешується у Redis із TTL 24 години;
   - Якщо перевірка підпису з кешованим ключем повертає помилку, адаптер виконує **одноразове примусове оновлення ключа** з API банку та повторює перевірку;
   - Якщо підпис не валідується і з новим ключем — спрацьовує fail-closed захист: запит негайно відхиляється.
3. **Fail-Closed поведінка:**  
   Якщо заголовок `X-Sign` відсутній або невалідний — обробник негайно повертає **`HTTP 401 Unauthorized`**. Жодних змін стану замовлення чи бази даних не виконується.

### 2.4. Надійна ідемпотентність та стійкість до повторів (Replay Protection)

Monobank надсилає вебхуки повторно (до 3 спроб), якщо не отримує код `HTTP 200`. Для надійної обробки впроваджується дворівневий захист:

1. **Durable Webhook Ledger у базі даних (Slice 2):**  
   Створюється таблиця журналювання подій `payment_webhook_events` із полями `(id, provider, invoice_id, status, modified_date, payload_hash, processed_at)`.
   Унікальний композитний індекс `(invoice_id, status, modified_date)` гарантує неможливість повторного застосування тієї самої транзакції.  
   _(У межах Slice 1 контракт ідемпотентності та захисту від дублікатів верифіковано через тестовий леджер `InMemoryTestWebhookLedger` із мʼютексною серіалізацією)._
2. **Короткоживучий Redis Mutex (Slice 2):**  
   Для запобігання стану гонитви (race condition) при одночасних паралельних ретраях від банку між різними процесами встановлюється розподілений лок `lock:payment:monobank:{invoiceId}` на 10 секунд.  
   _(У межах Slice 1 локальну атомарність команд і викликів вебхуків забезпечено внутрішнім per-invoice мʼютексом леджера)._
3. **Валідація бізнес-інваріантів перед мутацією:**  
   Перед зміною статусу замовлення обов'язково перевіряються:
   - Збіг суми `amount` (у копійках) із сумою замовлення в Medusa;
   - Валюта `ccy === 980` (UAH);
   - Коректність прив'язки `reference` до ідентифікатора замовлення/кошика.
4. **Семантика повторних запитів:**
   - Якщо валідна подія вже оброблена — повертається `HTTP 200 OK` без повторного запуску бізнес-воркфлоу;
   - У разі тимчасової внутрішньої помилки інфраструктури (наприклад, збій з'єднання з БД) — повертається `HTTP 500/503`, дозволяючи банку повторити доставку вебхука. Помилки не маскуються під `200 OK`.

### 2.5. Матриця співставлення статусів (Status Transition FSM)

Дозволено виключно односпрямовані переходи станів; зворотні переходи (backward transitions) суворо заборонені:

| Статус Monobank | Статус Medusa v2        | Опис та семантика                                    | Допустимі наступні стани                   |
| --------------- | ----------------------- | ---------------------------------------------------- | ------------------------------------------ |
| `created`       | `pending`               | Інвойс створено, очікується перехід покупця          | `processing`, `hold`, `failure`, `expired` |
| `processing`    | `pending`               | Покупець на платіжній сторінці, триває обробка / 3DS | `hold`, `success`, `failure`, `reversed`   |
| `hold`          | `authorized`            | **Кошти успішно заблоковано на картці** (до 9 днів)  | `success` (finalize), `reversed` (void)    |
| `success`       | `captured`              | **Платіж успішно фіналізовано** (кошти списано)      | `reversed` (refund)                        |
| `failure`       | `failed`                | Помилка оплати (недостатньо коштів, відмова)         | Фінальний стан                             |
| `reversed`      | `canceled` / `refunded` | Холд скасовано або кошти повернуто                   | Фінальний стан                             |
| `expired`       | `canceled`              | Термін дії інвойсу вичерпано                         | Фінальний стан                             |

_Будь-яка спроба перевести замовлення зі статусу `captured` назад у `authorized` або `pending` блокується FSM-контролером._

### 2.6. Оркестрація блокування коштів (Authorization Hold Orchestration)

Маркетплейс використовує двостадійну модель:

1. **Hold тривалістю до 9 днів:**  
   Інвойс створюється з параметром `paymentType: "hold"`. Згідно з офіційною специфікацією Monobank API, холд утримується банком **до 9 днів** (якщо протягом цього часу не викликано фіналізацію, холд автоматично скасовується банком без списання коштів).
2. **Фіналізація або скасування:**
   - Після підтвердження замовлення ремісниками викликається `POST /api/merchant/invoice/finalize` на повну суму заблокованого холду (часткова фіналізація суворо заблокована у Slice 1 для запобігання втрати залишку заблокованих коштів);
   - Якщо замовлення скасовано — холд знімається через скасування інвойсу без комісій за еквайринг для покупця.
3. **Розмежування понять:**  
   Цей механізм є **технічною оркестрацією банківського холдування (Authorization Hold)**. Він не є юридичним чи фінансовим депозитом (Escrow). Модель взаємовідносин платформи, покупця та майстрів, розподіл відповідальності та виплати ремісникам визначаються окремими пакетами рішень `COM-1`..`COM-5` у Phase 5.

### 2.7. Межі першої тестової реалізації (Scope)

У межах першого кодового слайсу (Slice 1) реалізуються базові транзакційні контракти та ядро адаптера:

1. Створення інвойсу з фіксованим режимом холдування (`POST /api/merchant/invoice/create`, `paymentType: "hold"`);
2. Отримання та редирект на `pageUrl`;
3. Fail-closed валідація сирого бінарного тіла та заголовка `X-Sign` через ECDSA з кулдауном 60с;
4. Строгі Zod runtime-схеми (`.strict()`) для вебхука та відповідей банку;
5. Захист від повторних списань: заборона автоматичних ретраїв (NO-RETRY) для мутуючих POST-запитів;
6. Розмежування скасування заблокованого холду (`POST /api/merchant/invoice/cancel`) та видалення неоплаченого інвойсу (`POST /api/merchant/invoice/remove`);
7. Запит статусу інвойсу (`GET /api/merchant/invoice/status`) із повною валідацією інваріантів під час синхронізації;
8. Фіналізація холду (`POST /api/merchant/invoice/finalize`) зі строгою перевіркою попереднього статусу `authorized` (заборона прямого переходу з `pending` у `captured`);
9. Тестова модель ідемпотентності та атомарності через `InMemoryTestWebhookLedger` із мʼютексною серіалізацією команд.

_Персистентна таблиця PostgreSQL `payment_webhook_events`, унікальні індекси БД та розподілений Redis-lock виносяться в наступний окремий етап (Slice 2). Специфічні нативні методи Apple Pay / Google Pay на рівні SDK відкладаються, оскільки базовий `pageUrl` банку вже нативно підтримує ці гаманці на платіжній сторінці._

## 3. Наслідки

### Позитивні

- Технічна готовність контрактного ядра пісочниці (Slice 1) до безпечного ізольованого тестування; бойова активація вимагає завершення Slice 2 (PostgreSQL/Redis) та проходження юридично-фінансових гейтів COM-1..COM-5;
- Бездоганний криптографічний захист від підробки фінансових повідомлень завдяки ECDSA;
- Надійна ідемпотентність, стійка до повторних спроб банку та паралельних запитів;
- Чітке співставлення статусів із запобіганням некоректним змінам стану замовлення.

### Негативні та ризики

- Необхідність утримання таблиці журналювання вебхуків та кешування публічного ключа;
- Залежність тестового прогону від зовнішнього тестового середовища банку (компенсується локальним моком).

### Що залишається суворо заблокованим

- **`allow_live_payment_gateway: false`** у файлі політики `infra/deployment-policy.json` залишається у заблокованому стані;
- Заборонено внесення бойових токенів еквайрингу до конфігурацій чи секретів хоста;
- Будь-які реальні фінансові розрахунки на живому сайті `https://life-mp.pp.ua/` залишаються суворо вимкненими.

## 5. Безпека та приватність

1. **Мінімізація PII:** Платформа Life-MP не зберігає і не обробляє номери банківських карток або CVV.
2. **Санітизоване логування:** Усі логи містять виключно несекретні ідентифікатори (`invoiceId`, `orderId`, `status`, `durationMs`).
3. **Ізоляція ключів:** Тестові токени передаються виключно через змінні середовища `MONOBANK_SANDBOX_TOKEN` у локальному файлі `.env.local` (у `.gitignore`).

---

## 6. Відкат або заміна

1. Модуль `@life/medusa-payment-monobank` вимикається в конфігурації `medusa-config.ts` без впливу на інші системи;
2. Поліморфна архітектура Medusa v2 дозволяє замінити провайдера без міграцій структури замовлень.

## 7. Етапи впровадження та дорожня карта (Implementation Slices)

Впровадження архітектури тестового шлюзу Monobank реалізується двома поетапними слайсами:

1. **Slice 1 (PR #80) — Local Sandbox Contract Core:**
   - Ядро адаптера `MonobankSandboxPaymentAdapter` із підтримкою hold-only режиму;
   - Строгий FSM: перехід `pending -> captured` без проміжного `authorized (hold)` категорично заборонено;
   - Валідація сирого бінарного тіла запиту проти заголовка `X-Sign` через ECDSA-SHA256;
   - Строгі Zod-схеми (`.strict()`) для тіла вебхука та відповідей банку;
   - Захист від DoS amplification: кулдаун 60 секунд на forced public key refresh;
   - `MonobankHttpTransport`: вилучено автоматичні retry для POST (дозволено лише для безпечних ідемпотентних GET);
   - Реалізація `getInvoiceStatus()` та синхронізації `syncInvoiceStatus()`;
   - Санітизована відповідь 503 без витоку деталей внутрішньої інфраструктури;
   - Локальний тестовий леджер `InMemoryTestWebhookLedger` із мʼютексним блокуванням для контрактних тестів;
   - Явна типізація помилки `MonobankReconciliationError` у разі розходження успіху провайдера та локального оновлення леджера.

2. **Slice 2 — Persistent Database Ledger & Distributed Lock:**
   - Міграція створення таблиці `payment_webhook_events` у PostgreSQL;
   - Унікальний індекс бази даних `(invoice_id, status, modified_date)`;
   - Розподілений мʼютекс на базі Redis для блокування між інстансами;
   - Інтеграційні тести збереження подій у PostgreSQL.
