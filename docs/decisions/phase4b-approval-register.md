## 2. Детальні матриці рішень Phase 4B

### COM-1 (LGL-1): Юридична модель маркетплейсу

```text
┌──────────────────────────────────────┬──────────────────────────────────────┬──────────────────────────────────────┐
│ Параметр порівняння                  │ Option A: Агентська модель (Agent)   │ Option B: Торговець запису (MoR)     │
├──────────────────────────────────────┼──────────────────────────────────────┼──────────────────────────────────────┤
│ Сторона договору з покупцем          │ Продавець-майстер (ФОП)              │ Платформа «ЛАЙФ»                     │
│ Дохід платформи для оподаткування    │ Лише агентська комісія (наприклад 10%)│ Повна вартість усіх товарів          │
│ Податковий ризик (Єдиний податок)    │ Мінімальний (комісія за послуги)     │ Високий (швидкий вихід за ліміти ЄП) │
│ Відповідальність за якість та гарантії│ Виробник (майстерня)                 │ Платформа «ЛАЙФ»                     │
│ Первинні документи з виробником      │ Акт наданих послуг / звіт повіреного │ Договір поставки / видаткова накладна│
└──────────────────────────────────────┴──────────────────────────────────────┴──────────────────────────────────────┘
```

- **Правове обґрунтування:** Згідно зі ст. 295–305 Господарського кодексу України та ст. 1000 Цивільного кодексу України, комерційне посередництво (агентська діяльність) дозволяє маркетплейсу приймати замовлення та кошти для подальшої передачі виробнику з утриманням агентської винагороди.

---

### COM-2 (FIN-1): Порівняння платіжних еквайрів

| Еквайр-провайдер        | Тариф комісії | Підтримка Marketplace Split   | Механіка холдування (Escrow)         | Інтеграція з Medusa v2 |
| ----------------------- | ------------- | ----------------------------- | ------------------------------------ | ---------------------- |
| **LiqPay (ПриватБанк)** | 1.3% – 1.5%   | Прямий спліт на IBAN/картки   | Pre-authorization hold (до 30 днів)  | REST API / Webhooks    |
| **WayForPay**           | ~2.0% – 2.2%  | Вбудований Marketplace Escrow | Автоматичне розблокування за ТТН     | REST API / Webhooks    |
| **RozetkaPay**          | ~1.5%         | Спліт-виплати на рахунки ФОП  | Холдування до підтвердження доставки | REST API / Webhooks    |
| **Fondy (Flow)**        | ~2.0%         | Multi-vendor Split            | Двоетапна авторизація                | REST API / Webhooks    |

- **Цільовий платіжний потік (Payment Lifecycle):**
  1. `Checkout` ➔ Авторизація платежу покупця (Hold коштів).
  2. `Order Splitting` ➔ Створення `ParentOrder` (загальний платіж) + `VendorChildOrder` для кожної майстерні.
  3. `Fulfillment` ➔ Відправлення посилки майстернею за згенерованою ЕН Нової Пошти.
  4. `Tracking Webhook (Статус 9: Вручено)` ➔ Списання коштів покупця (Capture) та зарахування в розрахунковий леджер (`VendorPayable`).
  5. `Settlement` ➔ Виплата на IBAN майстерні за вирахуванням комісії за графіком T+3.

### COM-3 (FSC-1): Схема фіскалізації через ПРРО

- **Провайдери хмарного ПРРО:** `Checkbox` (checkbox.ua) або `Вчасно.Каса` (vchasno.ua).
- **Схема розподілу фіскальної відповідальності:**
  - **Фіскалізація послуг платформи:** «ЛАЙФ» видає фіскальний чек або акт на суму утриманої комісії за інформаційно-посередницькі послуги.
  - **Фіскалізація вартості товарів:** Продавець-ФОП формує фіскальний чек на товар самостійно (або автоматизовано через API Checkbox за токеном каси ФОП) та надає його в електронному вигляді покупцю чи вкладає у посилку.

---

### LOG-1: Автоматизація логістики Нової Пошти

- **Модель логістики:** _Direct-from-Vendor_ (децентралізована відправка з майстерень).
- **Ланцюжок статусів ЕН (Nova Poshta Tracking):**
  - `1` — Створено ЕН (статус замовлення в системі: `processing`).
  - `4 / 5` — Посилка прямує до отримувача (`shipped`).
  - `7 / 8` — Прибуло у відділення / поштомат (`awaiting_pickup`).
  - `9` — **Посилку успішно отримано покупцем** ➔ **тригер розблокування виплати в Medusa Ledger (`SettlementBatch`)**.
  - `102 / 103` — Відмова від отримання / повернення відправнику ➔ запуск сценарію повернення коштів (Refund) та скасування `VendorPayable`.
