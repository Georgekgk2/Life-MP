# Інструкція: авторизоване обстеження продукційного сервера лише для читання

## Призначення та межа

Ця інструкція збирає мінімальний **санітизований** доказ, щоб вирішити, чи можна окремо спроєктувати майбутній проєкт Compose `life-prod`. Вона не є дозволом на продукційний запуск, підключення, зміни сервера, створення Compose-файла або використання наявного середовища.

Обстеження не знімає фундаментальних блокерів [COM-1, COM-2, COM-3, COM-5 і LOG-1](../decisions/launch-scope.md). До їх письмового прийняття оформлення замовлень, платежі, фіскалізація, відправлення, платні сервіси/події та партнерська програма залишаються вимкненими відповідно до [меж запуску](../decisions/launch-scope.md).

## Передумови й дозвіл

Обстеження дозволене лише після одноразового письмового дозволу власника продукційної інфраструктури. У дозволі мають бути одночасно вказані:

1. власник сервера та виконавець обстеження;
2. дата, часовий проміжок і мета: оцінити можливість **окремого** проєкту Compose `life-prod`;
3. дозволений лише наданий нижче набір команд лише для читання без `sudo`, без інтерактивної автентифікації та без передавання секретів;
4. канал для передання лише санітизованого звіту і власник його зберігання;
5. підтвердження, що відмова на будь-який пункт є допустимою й не дає права обходити обмеження.

Якщо такого дозволу немає, сервер не налаштований як вузол SSH або доступний лише через неавторизований канал, **не підключатися**. Зафіксувати в шаблоні стан «не виконано: немає дозволу/каналу», передати його власнику інфраструктури та чекати нового письмового дозволу. Не шукати інші адреси, облікові записи, ключі або способи доступу.

## Абсолютні заборони

Під час цієї інструкції заборонено:

- читати, шукати, копіювати, монтувати, передавати або цитувати будь-які Jorvis-артефакти: репозиторії, конфігурації, `.env`, резервні копії, томи, образи, журнали, секрети, ключі, токени, облікові дані чи дані користувачів;
- перевикористовувати наявні контейнери, мережі, томи, образи, порти, домени, сертифікати, облікові записи, Compose-проєкти або будь-які інші ресурси;
- виконувати `sudo`, змінювати списки контролю доступу/власників, інсталювати пакети, створювати файли, перенаправляти вивід у файл, редагувати конфігурацію, змінювати мережевий екран/DNS/маршрути або встановлювати з’єднання назовні;
- виконувати будь-які команди Docker для підготовки ресурсів, розгортання або руйнівних дій, зокрема `docker compose up`, `docker compose down`, `docker compose pull`, `docker compose build`, `docker run`, `docker create`, `docker start`, `docker stop`, `docker restart`, `docker rm`, `docker rmi`, `docker volume rm`, `docker network create`, `docker network rm`, `docker system prune`;
- виконувати `docker ps`, `docker inspect`, `docker logs`, `docker compose ls`, `docker compose config` або команди до конкретного контейнера, образу, тому, мережі чи Compose-проєкту: вони можуть розкрити або зачепити наявні ресурси;
- збирати повні IP-адреси, DNS-імена, імена вузлів, MAC-адреси, серійні номери, імена користувачів, імена процесів, командні рядки, вміст конфігурацій, змінні середовища, токени, паролі, приватні ключі, сертифікати, резервні копії, персональні або комерційні дані.

Будь-яка пропозиція вийти за ці межі зупиняє обстеження. Наступна дія — отримати окремий письмовий дозвіл, який описує лише потрібну додаткову категорію доказів; ця інструкція не є таким дозволом.

## Дозволений набір доказів лише для читання

Виконавець запускає лише команди з цього розділу, по одній, у погодженій сесії. Вони не змінюють стан сервера, не читають прикладні дані й не адресують наявні Jorvis або інші продукційні ресурси. Відсутня утиліта, помилка доступу або заборона політикою — валідний результат «невідомо», а не причина шукати обхід.

### Платформа та ізоляція ОС

```bash
uname -srmo
cat /etc/os-release
date -u +%Y-%m-%dT%H:%M:%SZ
getconf _NPROCESSORS_ONLN
free -h
df -hP /
findmnt -no FSTYPE,OPTIONS /
stat -fc %T /sys/fs/cgroup
docker version --format 'клієнт={{.Client.Version}} сервер={{.Server.Version}}'
docker compose version
```

Зафіксувати: сімейство ОС і ядро, архітектуру, часову мітку UTC, кількість доступних CPU, доступну/загальну пам’ять, розмір і вільне місце кореневої файлової системи, тип/параметри монтування для `/`, тип cgroup, а також лише версії Docker Engine і Compose або стан «недоступно». Не фіксувати шляхи Docker, драйвер зберігання, ідентифікатор інсталяції, перелік образів або стан інших контейнерів.

### Мережа та зовнішня межа

Виконавець не виконує жодних мережевих команд і не збирає мережеві відомості з хоста. Власник інфраструктури надає лише письмову категоріальну санітизовану атестацію, без фактичних назв, адрес, номерів портів, шлюзів, правил, ідентифікаторів або відомостей про інші навантаження:

- чи може бути виділена незалежна мережева/вхідна межа для майбутнього `life-prod`;
- чи існує публічний вхід без конфлікту з наявними ресурсами;
- чи дозволяє політика хоста ізольовану мережу Compose для майбутнього проєкту.

Для кожного пункту атестація містить лише `підтверджено` або `не підтверджено`. Відповідь `не підтверджено` або відсутність атестації є валідним результатом, а не причиною збирати додаткові мережеві дані або шукати обхід. Атестація «підтверджено» без відповідального власника та процедури зміни вважається недостатньою.

### Ємність та ізоляція майбутнього проєкту

Порівняйте санітизовані платфорні показники з **письмово погодженою** майбутньою оцінкою CPU, RAM, диска, журналів і резервного копіювання. Якщо такої оцінки немає, зафіксувати «місткість не може бути прийнята»; не підставляти припущення і не резервувати ресурси.

Для ізоляції потрібне письмове підтвердження власника інфраструктури, що майбутній проєкт зможе мати власні: назву Compose-проєкту `life-prod`, простір імен мережі без перетинів, іменовані томи, секрети, облікові записи сервісів, журнали, політику резервного копіювання та маршрути вхідного трафіку. Це вимога до майбутнього проєктування, а не команда створити будь-який з цих ресурсів.

Не вважати доступними ресурсами будь-що вже знайдене на сервері. Відсутність доказу про окремість означає, що ресурс треба вважати непридатним для `life-prod`.

## Правила санітизації виводу

1. Не надсилати сирий вивід термінала, скриншоти, історію команд або копію сесії.
2. Перед переданням замінити кожне ім’я вузла, адресу, маршрут, порт, інтерфейс, користувача, шлях, ідентифікатор, версію, серійний номер та будь-яке унікальне значення на `[ПРИХОВАНО]`, якщо воно не потрібне як агрегований висновок.
3. Зберігати лише категоріальні висновки: наприклад, «Compose: доступний», «пам’ять: достатність не оцінена», «мережева межа: письмово не підтверджена», «ізоляція: письмово не підтверджена».
4. Не маскувати секрет частково: будь-який підозрілий рядок не передавати взагалі. Якщо він уже потрапив до чернетки, видалити чернетку відповідно до політики власника каналу та повідомити власника інфраструктури без повторного пересилання значення.
5. Доказ має містити лише факти, необхідні для рішення нижче; додатковий збір даних заборонений.

## Рішення після обстеження

**Можна перейти лише до окремого проєктування `life-prod` Compose-контурів**, коли всі рядки шаблону прийняті, Docker і Compose доступні, є позитивна оцінка ємності, підтверджена окрема мережева/ресурсна ізоляція та призначені операційні власники. Рішення фіксує власник інфраструктури; воно не є дозволом на підготовку ресурсів, розгортання або комерційний запуск.

**Відмова від проєктування** настає одразу, якщо немає авторизації, будь-який доказ вимагає читання Jorvis-артефактів або використання наявного ресурсу, Docker/Compose не підтверджені, ємність не оцінена чи недостатня, мережева межа не доведена, ізоляція неповна або операційний власник відсутній. У цьому разі не проєктувати серверний контур на підставі неповних даних; повернути шаблон власнику інфраструктури з конкретним неприйнятим рядком.

Навіть позитивне рішення цієї інструкції не змінює меж запуску: продукційні торговельні можливості, усі платні сервіси й події та партнерська програма лишаються заблокованими або вимкненими, доки їхні окремі рішення та фундаментальні блокери не буде письмово прийнято.
